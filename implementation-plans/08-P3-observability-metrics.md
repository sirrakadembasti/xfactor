# P3: Observability, Metrics, and Dashboard Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `subagent-driven-development` or `executing-plans` to implement one delivery unit at a time. Read `PROJECT-CONTINUITY.md` first. Never execute a later unit before its dependencies are verified.

## Goal
Establish full read-only visibility into the quality pipeline's state, traceability, and historical trends. Provide a comprehensive observability dashboard, longitudinal metrics APIs, and requirement-impact/selective rebuild analysis, while keeping verification evidence immutable and independent of agent self-reports.

---

## Architecture

The P3 observability layer operates as a read-only view layer over the database schemas and artifact structures established in P0-P2. It does not introduce state transition commands or acceptance bypass operations.

```
       +---------------------------------------------------------+
       |                  Frontend Dashboard (UI)                 |
       +-------+--------------------+---------------------+------+
               |                    |                     |
               v                    v                     v
     [Dashboard & Runs]     [Traceability DAG]     [Metrics & Trends]
               |                    |                     |
               +----------+---------+----------+----------+
                          |                    |
                          v                    v
                  [Read-Only REST APIs] [Redaction Layer]
                          |                    |
                          +---------+----------+
                                    |
                                    v
                         [SQLite Evidence Store]
```

### 1. Data Retrieval and Query Layer
- Expose optimized read APIs for `project_contracts`, `requirements`, `verification_runs`, `verification_checks`, `repair_issues`, and `artifacts`.
- Query execution leverages secondary indexes created in previous phases (e.g., `idx_verification_checks_run`, `idx_repair_issues_run_req`).
- API controllers are purely read-only (HTTP GET) and reside in `backend/routes/projectRoutes.js`. They enforce strict project ownership authorization.

### 2. Longitudinal Metrics Engine
- Compute gate success rates, run durations, technology stack performance patterns, and common failure fingerprints.
- Error/failure fingerprints are generated by clustering error names and message signatures (removing unique identifiers, hashes, and timestamps).

### 3. Traceability Graph and Rebuild Analyzer
- Walk the requirement-to-evidence graph (`requirements` -> `requirement_task_links` -> `contract_tasks` -> `requirement_file_links` -> `artifact_files` -> `requirement_check_links` -> `verification_checks`).
- The rebuild analyzer matches changed requirements in a new draft contract with existing checkpoints, using the dependency graph to simulate which task checkpoints will be invalidated.

### 4. Security, Retention, and Redaction
- Read queries for logs and evidence excerpts pass through `redactSensitiveText`; raw secrets never reach the frontend.
- Verification runs/check rows, gate status, command, exit code, timestamps, digests, requirement/artifact links, and audit fingerprints are immutable and retained. Retention may compact/redact oversized raw excerpts inside `evidence_json` after 30 days, but must preserve their cryptographic digests and must never delete authoritative verification rows or relationship records.

---

## Tech Stack
- **Backend:** Node.js ESM, Express, SQLite (`node:sqlite`).
- **Frontend:** React (Vite), Tailwind CSS, Lucide React, ReactFlow (v11+) for graph visualization.
- **Testing:** Mocha/Assert for Node integration, JSDOM and React Testing Library for frontend behavior.

---

## Global Constraints
1. **Strictly Read-Only:** P3 modules must never expose write APIs that alter project completion status, override quality gates, or bypass verifier verdicts.
2. **Advisory Separation:** The UI must explicitly segregate "Agent Self-Reports" (advisory) from "Independent Sandbox Evidence" (authoritative).
3. **No Unredacted Secrets:** High-volume stdout/stderr verification check outputs must be redacted in the backend before transmission.
4. **Performance Bounds:** All metrics queries must run within a 150ms database threshold; use raw SQL aggregates and cover indexes.
