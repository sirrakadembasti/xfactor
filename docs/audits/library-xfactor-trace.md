# Library delivery: XFactor source trace

Scope: read-only examination of XFactor source and the delivered `kutuphane-takip-sistemi-2.zip`. These are generator and verifier risks, not claims that the delivered app failed an execution check. The independent delivery audit should attach its runtime results before treating a risk below as the cause of a specific defect.

## Navigation and evidence method

I queried `graphify-out/graph.json` (1,989 nodes, 5,327 links) for generator and verification nodes and the `imports` edges. It identifies `runChecks.js` → `smokeVerifier.js` → `databaseVerifier.js`, `apiVerifier.js`, `browserVerifier.js`, and `testInfrastructureVerifier.js` as AST imports. The Python `graphify query` command was unavailable (`No module named graphify`); the repository's own [graph report](../../graphify-out/GRAPH_REPORT.md) says static calls are resolved only when there is a single target and the graph cannot establish runtime behavior or all data flow. Each claim below is therefore checked against source. I inspected selected ZIP entries in memory without extraction or app execution.

## Findings and proposed fixes

1. **Runtime gates can aggregate partial checks as complete.** The policy lists expected members for each runtime gate in [qualityPolicy.js](../../backend/verification/qualityPolicy.js#L52-L83), but `combineRuntimeGate` passes when *any* member is present and no included member fails or blocks; it never requires the full applicable member set ([qualityPolicy.js](../../backend/verification/qualityPolicy.js#L509-L555)). [artifactVerifier.js](../../backend/verification/artifactVerifier.js#L267-L270) synthesizes these gates from worker checks, then marks an artifact verified when every *present* check passes ([artifactVerifier.js](../../backend/verification/artifactVerifier.js#L316-L356)). A missing member or missing non-runtime mandatory gate needs an explicit blocked result. **Fix:** define applicability per contract/stack, require every applicable member, and evaluate the complete `MANDATORY_GATES` set before artifact status changes. **Acceptance:** a worker response omitting `database_write_capability`, `api_query_check`, or any mandatory gate cannot yield a verified artifact; a complete passing set can.

2. **Database and API evidence does not prove persistence.** [databaseVerifier.js](../../backend/verification/databaseVerifier.js#L14-L29) probes `fs.existsSync` for the schema and database, then calls file existence a passed connectivity and write-capability check. [apiVerifier.js](../../backend/verification/apiVerifier.js#L57-L77) sends a generic POST and GET to `/api/<domain>`, checks 2xx status, and calls a successful POST response a `database_mutation_assertion`. It does not compare records before and after or inspect SQLite state. The library artifact has multiple entity and loan routes, while this verifier exercises only generic `name`, `title`, and `description` fields. **Fix:** require contract-specific fixtures and expected response/DB assertions, including create/read/update/delete, loan/return stock transitions, invalid input, and restart persistence where applicable. Use a private verification database. **Acceptance:** a 2xx API that discards writes, a read-only SQLite file, and a loan API that fails to adjust stock each fail their respective gates.

3. **Browser journey can pass without interactive behavior.** [browserVerifier.js](../../backend/verification/browserVerifier.js#L1-L73) fetches HTML and supports navigation, reload, and string/element checks; it does not perform clicks, form entry, or client-side state assertions. When no browser contract exists, [smokeVerifier.js](../../backend/verification/smokeVerifier.js#L10-L26) infers only `/` plus a `<main>` assertion. The ZIP contains book, category, member, loan, and admin pages, so this inferred check covers only a small fraction of its stated workflow. **Fix:** require explicit user journeys for mandatory domain operations and execute them in a real browser with isolated data. **Acceptance:** a page with a `<main>` tag but broken add-book or return-loan interaction fails.

4. **Generated test baseline and test gate can give false confidence.** For Next.js, [codeGenerator.js](../../backend/engine/codeGenerator.js#L505-L519) creates a `test` script that prints `No tests specified` and exits zero. [testInfrastructureVerifier.js](../../backend/verification/testInfrastructureVerifier.js#L30-L45) checks only that a script exists, then treats `npm test` exit zero as a passed test suite ([testInfrastructureVerifier.js](../../backend/verification/testInfrastructureVerifier.js#L47-L70)). The delivered ZIP overrides this with `tsx --test tests/library.test.ts`, so this is a generator risk rather than an assertion about this ZIP's test content. **Fix:** remove the passing placeholder, require at least one discovered substantive test linked to contract behaviors, and fail if the runner reports zero tests. **Acceptance:** the scaffold default and an empty test suite cannot pass; a library test that verifies loan/return invariants can.

5. **Scaffold package and Docker contract is fragile.** [codeGenerator.js](../../backend/engine/codeGenerator.js#L559-L607) rewrites `package.json`, uses `latest` for many dependencies and `^1.0.0` for unknown imports, while the generated Next.js Dockerfile runs `npm ci` ([codeGenerator.js](../../backend/engine/codeGenerator.js#L798-L827)). The delivered ZIP contains both `package-lock.json` and a Dockerfile matching that template, but source inspection alone cannot establish whether its lockfile matches the rewritten package manifest or whether the image builds. The Dockerfile copies Prisma files yet does not run `prisma db push` on startup, and no volume is declared. **Fix:** resolve and lock dependencies after the final manifest edit, validate `npm ci`, build the image, and document or automate private database initialization and persistent storage. **Acceptance:** a clean `npm ci` and Docker build/run succeed from the final ZIP; a fresh container initializes its schema through an explicit safe path and persistence survives a restart when configured.

6. **README defaults can omit a necessary seed step.** The generic README generator writes install, Prisma generate/push, environment, and start commands, with no seed command ([readmeGenerator.js](../../backend/engine/readmeGenerator.js#L109-L157)). This delivery's authored README separately warns that its seed is destructive and omits it from routine startup, which may be appropriate for a fresh empty app. **Fix:** make seed documentation conditional on the project's actual startup contract, and explicitly distinguish required initialization from destructive sample data. **Acceptance:** a fresh install following only README steps reaches the stated first-use journey; optional destructive seed has a warning and an isolated-database verification path.

## Limits

I did not run the app, tests, Docker, or XFactor. The ZIP's package manifest, Dockerfile, service manifest, route/page list, and README were read in memory. Claims about build success, endpoint behavior, and data persistence require the separate isolated delivery audit. The graph supports navigation, not proof of causation.
